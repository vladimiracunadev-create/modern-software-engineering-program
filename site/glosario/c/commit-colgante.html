Definición

Objeto que ninguna referencia alcanza y que sigue en la base hasta la poda.

Definición de trabajo de SE-194 — Commits atómicos, historial y recuperación.

Por qué importa

La clase donde se define, SE-194 — Commits atómicos, historial y recuperación, existe con este propósito: la clase existe para que cada commit sea una unidad que se pueda revisar, localizar y deshacer, y para que, cuando alguien se equivoca, la respuesta sea una recuperación planificada y no una búsqueda a ciegas.

Cómo funciona

Según SE-194 — Commits atómicos, historial y recuperación:

En un repositorio con un archivo confirmado se simularon seis situaciones y se buscó el texto perdido en toda la base de objetos. Un commit seguido de reset --hard HEAD~1: sigue (y el reflog apunta a él). Un cambio agregado al índice y luego reset --hard: sigue como blob suelto. Un cambio editado sin agregar y luego reset --hard: no sigue. Un archivo no rastreado y luego clean -fd: no sigue. Un stash seguido de stash drop: sigue como commit colgante. Un commit, un reset, la expiración del reflog y gc --prune=now: no sigue. El resultado fue idéntico con Git 2.55 en Windows y 2.43 en Ubuntu.

Ejemplo

La clase no ilustra este término por separado; el ejemplo de su tema está en la sección «Ejemplo profesional» de SE-194 — Commits atómicos, historial y recuperación:

En la plataforma, cada cambio a penal.py va en un commit con una frase de resumen, un cuerpo que explica la regla de negocio afectada y un pie con el issue. Una prueba corta (pytest -q tests/test_penal.py) se ejecuta con git bisect run cuando una nota sale mal. El equipo exige que cada commit de una rama compile, de modo que la bisección no deba omitir puntos.

Errores y confusiones comunes

Las clases no registran un error exclusivo de este término. Los errores frecuentes del tema donde se enseña (SE-194 — Commits atómicos, historial y recuperación) son:

  • La bisección no señala un solo commit — causa: hay un commit que no compila junto al defecto. Corrección: reordenar la rama para que cada paso compile y repetir.
  • Hay que leer cientos de líneas tras la bisección — causa: el commit culpable mezcla varias intenciones. Corrección: dividir los commits con git add -p antes de publicarlos.

Límites y cuándo no aplica

Las clases no fijan un límite propio para este término. Los límites del tema donde se enseña (SE-194 — Commits atómicos, historial y recuperación) son: Las definiciones son operativas para la plataforma de entregas. No convierten términos con historia más amplia en sinónimos y deben contrastarse con la documentación primaria enlazada al final. Se ejecutaron tres experimentos con repositorios temporales en Windows y Ubuntu (WSL2) con resultados idénticos. La prueba de bisección fue determinista, el remoto no tenía protección, las historias son de 64 cambios de dos líneas y no se midió a ninguna persona leyendo ni un repositorio real. La siguiente clase pregunta qué pasa cuando varias personas hacen commits a la vez en ramas distintas y cómo se integran.
