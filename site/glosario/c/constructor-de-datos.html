Definición

Función que crea un dato de prueba con valores por defecto y permite cambiar solo lo relevante.

Definición de trabajo de SE-428 — Datos deterministas y gestión de fixtures.

Por qué importa

La clase donde se define, SE-428 — Datos deterministas y gestión de fixtures, existe con este propósito: la clase existe para que prepares el estado de cada prueba de forma que el resultado dependa solo del código y de los datos declarados, y para que identifiques y elimines las fuentes de no determinismo (orden de ejecución, azar, hora, identificadores, orden de colecciones).

Cómo funciona

Según SE-428 — Datos deterministas y gestión de fixtures:

Un conjunto de reglas evita discusiones y accidentes: los datos son sintéticos y nunca copias de producción; cada prueba declara solo los datos que le importan (el resto toma valores por defecto de un constructor); los valores con significado de negocio se nombran (plazo_vencido, nota_en_el_limite) y no se escriben como números sueltos; y toda fuente de azar recibe una semilla que se registra. Los constructores de datos de prueba (builders) reducen el acoplamiento a los cambios de esquema respecto de grandes archivos de datos compartidos.

Ejemplo

La clase no ilustra este término por separado; el ejemplo de su tema está en la sección «Ejemplo profesional» de SE-428 — Datos deterministas y gestión de fixtures:

El equipo de la plataforma adopta cuatro reglas. Primera: cada prueba de servicio abre una transacción sobre una base creada una vez por proceso y la deshace al terminar; las pruebas de migración, que hacen commit, crean su propia base. Segunda: la suite se ejecuta cada noche en un orden aleatorio con semilla impresa; un fallo se repite con --semilla. Tercera: toda prueba con datos aleatorios recibe un generador con semilla de un único punto, y la semilla va en el informe.

Errores y confusiones comunes

Las clases no registran un error exclusivo de este término. Los errores frecuentes del tema donde se enseña (SE-428 — Datos deterministas y gestión de fixtures) son:

  • Las pruebas pasan una a una y fallan juntas — causa: estado compartido mutable. Corrección: transacción con retroceso o base nueva por prueba.
  • Una prueba falla una vez de cada diez — causa: datos aleatorios sin semilla o propiedad mal enunciada. Corrección: registrar la semilla y revisar la propiedad.

Límites y cuándo no aplica

Las clases no fijan un límite propio para este término. Los límites del tema donde se enseña (SE-428 — Datos deterministas y gestión de fixtures) son: Las definiciones son operativas para la plataforma de entregas y deben contrastarse con la documentación primaria enlazada al final. Se ejecutaron tres experimentos con una base SQLite en memoria, una propiedad con datos sintéticos y procesos locales en Windows y Ubuntu (WSL2) con salidas idénticas salvo las cifras que dependen del sistema o de la ejecución, declaradas arriba. Cinco de las doce pruebas dependen del estado compartido por diseño, y la propiedad falla por un efecto del redondeo escogido por el autor.
