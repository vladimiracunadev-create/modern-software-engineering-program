Definición

Documento que declara el uso previsto, la evaluación y las limitaciones de un modelo.

Definición de trabajo de SE-291 — Machine learning como componente de producto.

Por qué importa

La clase donde se define, SE-291 — Machine learning como componente de producto, existe con este propósito: la clase existe para que trates un modelo de aprendizaje automático como un componente con contrato, límites y fallos propios dentro de un producto, y no como una caja que «tiene una exactitud».

Cómo funciona

Según SE-291 — Machine learning como componente de producto:

Una tarjeta de modelo (Mitchell et al.) documenta el uso previsto, los datos de evaluación, las métricas por subgrupo y las limitaciones conocidas. Sirve para que quien integra el modelo sepa para qué no sirve. El producto necesita además un plan de respaldo: qué se muestra cuando el modelo no tiene datos suficientes, cuando la confianza es baja o cuando está apagado; y un mecanismo para que la persona afectada o quien la atiende pueda cuestionar el aviso. El marco de gestión del riesgo del NIST ordena este trabajo en gobernar, mapear, medir y gestionar; no sustituye el criterio de dominio.

Ejemplo

Contexto concreto en el que aparece el término, de la sección «Ejemplo profesional» de SE-291 — Machine learning como componente de producto:

El equipo de la plataforma redefine el aviso como una decisión: «cada lunes, listar a los estudiantes con riesgo alto, con el motivo, para que el docente decida si escribe». Fija una línea base (sin entregas en dos semanas) y exige que el modelo la supere en sensibilidad con el mismo número de avisos. Separa entrenamiento y prueba por fecha, revisa cada variable con la pregunta de la fuga (descarta «nota final» y «fecha de baja»), reporta sensibilidad, valor predictivo y prevalencia, y documenta la tarjeta del modelo.

Errores y confusiones comunes

Ningún error de las clases nombra este término; estos son los errores frecuentes del tema donde se enseña (SE-291 — Machine learning como componente de producto) son:

  • Exactitud excelente en prueba y mala en uso — causa: fuga o partición que no imita el uso. Corrección: separar por fecha y revisar cada variable con la pregunta de existencia.
  • «Avisa por casi todos» — causa: prevalencia baja con umbral por defecto. Corrección: reportar valor predictivo y elegir el umbral por coste de errores.

Límites y cuándo no aplica

Ninguna clase fija un límite propio para este término; estos son los límites del tema donde se enseña (SE-291 — Machine learning como componente de producto) son: Las definiciones son operativas para el aviso de riesgo. No convierten términos con una historia más amplia en sinónimos y deben contrastarse con la documentación primaria enlazada al final. Se ejecutaron tres simulaciones con datos sintéticos en Windows y Ubuntu (WSL2) con resultados idénticos. No se entrenó ningún modelo real, no se usó ninguna biblioteca de aprendizaje automático y no se midió ninguna población: los casos, el clasificador por umbral y las distribuciones son construcciones del autor.

Fuentes

Fuentes de las clases donde se enseña (cada una respalda el mecanismo que su clase indica):

  • Sculley et al., «Hidden Technical Debt in Machine Learning Systems» (NeurIPS, 2015) — deuda técnica específica de sistemas de aprendizaje automático; autoridad: NeurIPS.
  • Kaufman et al., «Leakage in Data Mining» (ACM TKDD, 2012) — formulación de la fuga de datos; autoridad: ACM Transactions on Knowledge Discovery from Data.
  • Mitchell et al., «Model Cards for Model Reporting» (FAT*, 2019) — documentación de uso previsto y límites de un modelo; autoridad: ACM FAT*.
  • Google, «Rules of Machine Learning» — prácticas de ingeniería de aprendizaje automático en producción; autoridad: Google Developers.
  • NIST, AI Risk Management Framework — marco de gestión del riesgo de sistemas de inteligencia artificial; autoridad: NIST.
